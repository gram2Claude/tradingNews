## ⚠️ Серьёзные пробелы

### 1. Конфликт «PR-тональность» vs «трейдинговые решения» 🚨

В спеке цель — **трейдинговые решения**, тональность — **PR**. Это противоречие.

Пример: «X5 открывает 200 новых магазинов» = **PR-позитив**, но для котировок может быть
**негатив** (рост капзатрат, давление на маржу). И наоборот: «X5 закрывает 100 убыточных
точек» = **PR-негатив**, для акций **позитив** (повышение эффективности).

**Что предлагаю:** хранить **обе** оценки.
в данном случае нас интересует именно тональность — **PR**.
финальная оценка **трейдинговые решения** будет принята на поздних этапах, когда мы добавим другие источники данных - телеграм каналы, торговые рекомендации, котировки биржи и тд.

```sql
ALTER TABLE news ADD COLUMN mood_pr TEXT;        -- pos|neutral|neg
ALTER TABLE news ADD COLUMN mood_trading TEXT;   -- pos|neutral|neg
ALTER TABLE news ADD COLUMN mood_reason TEXT;
```

Один промпт, две оценки — стоимость почти не растёт.
**Решение нужно:** оставить только PR / добавить вторую колонку / заменить на trading.
Решение: оставить только PR
### 2. Нормализация русских имён 🚨

В seed: «Игорь Шехтерман». В тексте новости встретится:
- «Шехтерман» (одна фамилия)
- «И. Шехтерман» (инициал)
- «Шехтермана» (родительный падеж)
- «Игорю Шехтерману» (дательный)
- «Игоря Шехтермана сообщил...» (винительный)

LLM может вернуть любой вариант. Простой `WHERE full_name = ?` не сматчит. Без
нормализации `persons.csv` будет с дублями и частоты поплывут.

**Что нужно добавить в план (T3):**
- В seed-таблицу — колонка `aliases` (массив): `["Шехтерман", "И. Шехтерман", "I. Shekhterman"]`
- Либо нормализация через `pymorphy3` (лемматизация русских словоформ) — в `requirements.txt`
- Промпт явно требует от LLM: **верни ровно ту форму, что в seed-таблице**.
  Это снимает 80% случаев.

  решение:  нормализация через `pymorphy3`

### 3. Нет retry / error handling на LLM-вызовах

В T3 — «один запрос на новость», и всё. Что если:
- Rate limit (429) → весь батч падает, статус остаётся `new`, на следующем часу
  повторяем = удвоенный счёт
- Сеть отвалилась посреди батча → половина проанализирована, половина нет
- LLM вернул невалидный JSON → exception, status не обновлён

**Что нужно:**
- `tenacity` для retry с экспоненциальной задержкой
- При невалидном JSON — `status='error'`, `error_msg`, не зависать
- Логировать `cost_tokens` в новую колонку `news.tokens_used` — увидишь стоимость напрямую

### 4. Часовые пояса

`published_at` с x5.ru — Москва (UTC+3). `fetched_at` — UTC. Если новость пришла
31 января в 23:30 МСК = 1 февраля 20:30 UTC → попадёт в папку `2026/2026_02/`
вместо `2026/2026_01/`. Месячные отчёты съедут.

**Что нужно:** хранить `published_at` явно в UTC, а для генерации пути использовать
`tz=Europe/Moscow`. Одна строка в `reporter.py`, но в плане не указано.

решение: всегда используем `tz=Europe/Moscow`

## ✅ Что хорошо

- SQLite как источник истины, отчёты генерируются → правильно
- `UNIQUE(source_id, url)` для дедупа → правильно
- Частоты не хранятся, считаются на лету → нет дрифта
- Этапы T1–T5 разделены чисто, каждый имеет acceptance
- Раздел «Что НЕ делаем» — отличная гигиена скоупа

## 🟡 Мелочи (DX)

- Команда `run` делает и fetch и analyze. Лучше разбить: `fetch`, `analyze`,
  `report`, `cycle` (все три). Удобно отлаживать порознь.
- Нет `python -m src status` — посмотреть «сколько new, сколько analyzed, сколько
  error». Это первая команда, которую захочешь.
- Нет `--company X5` фильтра. На MVP не критично, но добавь сейчас — иначе при
  добавлении компании 2 будешь рефакторить CLI.
- Slug из заголовка через транслитерацию — какая библиотека? Не указано.
  Рекомендую `transliterate`.
