Подключить второй источник новостей — **rbc.ru** — со следующими требованиями:

1. **Не парсить всё подряд**, а только новости, относящиеся к:
   - конкретному периоду (глобальная `start_date` или `start_date` компании);
   - конкретной компании (название + бренды);
   - конкретным аффилированным лицам (фамилии из `seed_persons`).

2. **Предварительная фильтрация** — нужно избегать скачивания тысяч нерелевантных
   статей. Решить как.

3. **Маскировка под пользователя** — сайт может определять бота и блокировать.
   Решить как.

То есть **архитектурный новый код = только `src/sources/rbc.py`** + пара строк в

## Premise Challenge

### P1. RBC использует **поиск с фильтром по дате** как основной discovery-канал

У rbc.ru есть три потенциальных канала:
- **(A) Поиск** `https://www.rbc.ru/search/?query=<компания>&dateFrom=DD.MM.YYYY&dateTo=DD.MM.YYYY` — точный по дате и теме, отдаёт ленту результатов.
- **(B) Тег-страницы** `/tags/?tag=<X5>` — может быть, но не у всех компаний есть свой тег, и листинг не фильтрует по дате.
- **(C) RSS** `https://rssexport.rbc.ru/...` — только топ-новости, слишком общий поток, по теме не фильтрует.

Рекомендация: **(A) Поиск** как основной канал. Запрос с `dateFrom = max(global.start_date, last_fetched_published_at)`, `dateTo = today`. Это и есть pre-фильтрация по периоду + теме — сразу попадаем в нужную выборку.

### P2. Двухэтапная фильтрация: listing → keyword filter → article

Даже после поискового запроса возвращается много "X5" в нерелевантном контексте
(упоминания вскользь, реклама, обзоры рынка). Поэтому:

- **Этап 1 — listing-фильтр.** Из результатов поиска берём `headline + lead`
  (превью текста). Применяем case-insensitive substring match по объединённому
  списку ключевых слов:
  - Алиасы компании: `X5`, `Х5`, `X5 Retail Group`, `X5 Group`
  - Бренды из `seed_persons.brand` (для X5: `Пятёрочка`, `Перекрёсток`, `Чижик`)
  - Фамилии лиц из `seed_persons.full_name` (для X5: `Шехтерман`, `Наумова`, …)
  
  Если ни одно слово не найдено в `headline + lead` → **пропускаем**, статью не
  скачиваем.

- **Этап 2 — full article.** Прошедшие фильтр URL качаем целиком, парсим, кладём
  в `news` со статусом `new`. Дальше — стандартный pipeline (analyzer → reporter).

Эффект: 1 запрос к листингу → 10-20 URL → ~3-5 действительно скачиваемых статей.

**Вопрос #2 — Принимаешь двухэтапную фильтрацию?**
Альтернатива: скачивать всё подряд, фильтровать после LLM-анализа. Я этот вариант
не рекомендую — лишние LLM-вызовы стоят денег и времени, а пред-фильтр на
substring почти бесплатный.

Твой ответ: да, Принимаю двухэтапную фильтрацию


### P3. Анти-бот защита — три уровня

**Уровень 1 — HTTP-гигиена (стартовая конфигурация):**
- Реалистичный User-Agent (актуальный Chrome desktop, обновляется раз в полгода).
- Полный набор заголовков: `Accept`, `Accept-Language: ru-RU,ru;q=0.9`,
  `Accept-Encoding: gzip, deflate, br`, `Referer` (главная rbc.ru для первого
  запроса, страница поиска для последующих).
- Cookie jar в памяти `httpx.Client` — RBC ставит сессионные cookies на главной,
  и без них поиск может вести себя иначе. Первый запрос идёт на `https://www.rbc.ru/`
  → потом на поиск.
- Случайная задержка между запросами: `uniform(3, 7)` секунд.
- Лимит на цикл: не более 30 запросов к rbc.ru за один `cycle`.
- `follow_redirects=False` + ручная валидация Location-хоста в allow-list
  `{www.rbc.ru, rbc.ru}` — повторяем SSRF-защиту из `x5_ir`.

**Уровень 2 — backoff на блокировки:**
- При `403 / 429 / 503` → ждём 60s, retry до 2 раз.
- Если всё равно блок → сохраняем URL в БД со статусом `blocked` (новый), в
  следующем цикле пробуем повторить. После 5 неудач — переводим в `error`.

**Уровень 3 — headless browser (deferred):**
- Playwright со stealth-пресетом (`navigator.webdriver=false`, реалистичный
  viewport, runtime fingerprint).
- ~200MB зависимостей, в 5-10× медленнее.
- Включаем **только если** уровни 1-2 не пробивают — добавляем потом отдельной
  спекой.

Рекомендация: **уровни 1+2 в MVP, уровень 3 как deferred**.

### P4. Парсинг тела статьи — DOM-структура

RBC использует разметку:
- `og:title` → `headline`
- `meta[name="mediator_published_time"]` или `article:published_time` → `published_at` (UTC)
- `.article__text` или `.article__content` — основной блок статьи
- Чистим: `.article__inline-item`, `.banner`, `.article__tags`, "Читайте также"

Эти селекторы — best-guess по моему знанию rbc.ru, **они могут устареть**.
Перед стартом T-фазы я открою 2-3 актуальных RBC-статьи через WebFetch и проверю
DOM. Если что-то изменилось — поправлю в плане 02.

## Безопасность (review для CSO будет отдельным шагом)

| Угроза | Митигация |
|---|---|
| SSRF через redirects | `follow_redirects=False` + allowlist `{www.rbc.ru, rbc.ru}` |
| Prompt injection в теле новости | SYSTEM_PROMPT уже инструктирует игнорить — переиспользуется |
| Утечка заголовков в DEBUG-логах | `httpx`/`httpcore` логгеры pinned to INFO (уже есть в `cli.py`) |
| DoS на rbc.ru с нашей стороны | Задержки 3-7s + лимит 30 req/cycle + backoff на 429 |
| Хранение cookies на диске | Не храним — cookie jar только в памяти процесса |
| Логирование URL-параметров | `published_at`, `url` мы и так логируем; запросов к API нет |

## Out of scope (явно отложено)

- Real-time стрим RBC (WebSocket / SSE) — нам хватает периодического fetch.
- Платный API РБК — даже если есть, мы вне корпоративного контекста, юзаем публичный сайт.
- Парсинг РБК-Pro (платная зона) — не интересует.
- Парсинг видео/подкастов — только текст.
- Telegram-каналы РБК — отдельный источник, отдельная спека.
