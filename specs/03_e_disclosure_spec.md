Подключить **e-disclosure.ru** как источник официальных раскрытий публичных
эмитентов (X5 и будущих компаний). Это **самый market-moving сигнал** для
трейдинговых решений:
- Квартальные и годовые отчёты
- Существенные факты (сделки M&A, смена менеджмента, дивиденды)
- Корпоративные действия (собрания акционеров, выкупы)

X5 как публичный эмитент **обязан** раскрывать эти события по 224-ФЗ.

## Что вскрыл recon (T7.1)

Подробности в `tests/fixtures/EDISCLOSURE_RECON.md`. Кратко:

- `www.e-disclosure.ru` закрыт **agressive anti-bot защитой `servicepipe.ru`**
  (российский WAF, аналог Cloudflare Bot Management)
- Через httpx без выполнения JS — **все endpoints возвращают 403**
- После 3-5 запросов с одного IP — IP throttle на 15-60 минут
- Никакого публичного RSS / открытого API / CSV-дампов нет
- robots.txt раскрывает структуру (`/api/*`, `/Company/Search?*`,
  `/Event/Certificate?*`), но **всё за тем же WAF**

**Единственный реалистичный путь:** Playwright (или эквивалент с JS-движком).

Это **существенное архитектурное расширение** — нужен новый базовый класс
`PlaywrightSource` в `src/sources/base.py`, который держит lifecycle браузера.

### P1. Bundle или split — задача 03 vs 03+04

**Вариант A (bundle):** Задача 03 = Playwright инфра + EDisclosureSource в одном PR.
- ✅ Один PR = одно ревью, проще merge
- ✅ Playwright обкатывается на реальном источнике сразу

- ❌ Если e-disclosure окажется частично проблемным — Playwright инфра тоже
  блокируется

**Вариант B (split):** 03 = только PlaywrightSource ABC + smoke test (например,
`page.goto("https://example.com")` работает). 04 = EDisclosureSource поверх 03.
- ✅ Чище архитектурно
- ✅ Меньшие PR, проще ревью каждый

- ❌ Playwright без реального консьюмера — труднее объяснить ценность

**Рекомендация: A (bundle).** Для personal-tool MVP режима скорость важнее,

### P2. Какие именно раскрытия X5 нас интересуют

E-disclosure классифицирует раскрытия по типам. Полный набор:

- **Существенные факты** (most market-moving): сделки, смены менеджмента,
  дивиденды, выкуп акций
- **Квартальные отчёты** (financial statements): MSFO, RSBU
- **Годовые отчёты**
- **Решения совета директоров**
- **Аффилированные лица** (изменения)
- **Собрания акционеров** (повестка, протоколы)
- **Эмиссионная документация** (новые выпуски, изменения)
- **Сообщения о сделках** с собственными ценными бумагами

**Вариант A — все типы:** просто, но шумно (например, ежемесячные «списки аффилированных лиц» — формальные публикации без новостной ценности).

**Вариант B — фильтр на market-relevant:** существенные факты + квартальные/годовые отчёты + крупные решения СД + сделки с акциями.
Остальное — пропустить.

**Рекомендация: A для MVP** — собираем все, классифицируем позже. Лучше иметь данные и не использовать, чем понять через 3 месяца что нужный тип не собирали.

Твой ответ: Вариант A


### P3. Backfill — нужен ли исторический

E-disclosure хранит **архив всех раскрытий за годы**. Через Playwright технически
доступен. Варианты:

**A) Без backfill** (как RBC): фетчим только с момента включения, start_date =
дата запуска.

**B) Backfill за N последних месяцев / лет.** При старте делаем один большой
prefill, потом инкрементально. Полезно для построения базовой картины
сентимента, тренда количества раскрытий.

Backfill через Playwright **медленный** (500ms × N статей). Например, 1 год X5
раскрытий ≈ 100-200 событий = 1-2 минуты браузерного времени, приемлемо
сделать один раз.

**Рекомендация: B, backfill за 6 месяцев** при первом запуске. Это даст
полную картину для тренинга / сравнения. Дальше — инкрементальный fetch.

Твой ответ: дата начала 2026-05-01


### P4. Частота fetch

Раскрытия публикуются эмитентами **в течение рабочего дня**, реже вечером /
ночью.

**Варианты:**
- A) Раз в час (как RBC) — даёт <1 час задержки, 7000+ Playwright-сессий/неделю
- B) Раз в 4 часа — приемлемая задержка для не-day-trading, 168 сессий/неделю
- C) Раз в день — для personal-tool достаточно, 7 сессий/неделю

**Рекомендация: B (раз в 4 часа)** для personal use. Раскрытие квартального
отчёта обычно ждут весь день в любом случае, час задержки не критичен.

Твой ответ: раз в 4 часа. но сейчас запуск только по моей команде


### P5. Playwright — headless vs headed

- **Headless** — обычный production режим. Быстрее, меньше памяти, никаких UI.
- **Headed** (`headless=False`) — видно окно браузера, удобно для дебага.

**Рекомендация:** в коде по умолчанию `headless=True`, переменная окружения
`PLAYWRIGHT_HEADLESS=false` для опционального дебага.

### P6. Где хранить browser context (cookies session)

Playwright `BrowserContext` хранит cookies — важно для servicepipe
(после challenge'а cookies нужны для последующих запросов в той же сессии).

**Варианты:**
- A) `context` в памяти процесса — каждый запуск с нуля решает challenge
- B) Persistent context — cookies сохраняются между запусками в
  `data/playwright_state/`. Быстрее, но возможно "залипшие" stale cookies

**Рекомендация: A для начала** (cleaner, predictable). При проблемах с
производительностью — переключим на B отдельной мини-спекой.

Твой ответ: A для начала


### P7. Selection эмитента — как находить X5 на e-disclosure

**Официальное юридическое название российской публичной X5:**
**«Корпоративный центр ИКС 5»** (это та публичная сущность, которая
раскрывает информацию на e-disclosure). Подтверждено пользователем,
сайт использует именно эту форму.

e-disclosure идентифицирует эмитентов по:
- **OGRN** (основной государственный регистрационный номер)
- **INN** (ИНН)
- **internal id** (на сайте — числовой ID, типа `/portal/company.aspx?id=1380`)

В T7.2 (Playwright живой recon) нужно:
1. Открыть `/Company/Search?query=Корпоративный+центр+ИКС+5` через Playwright
2. Найти конкретный internal id, ИНН и ОГРН
3. Зафиксировать в `companies.X5.e_disclosure_id` в config.yaml

**Это решение также требует обновить `companies[X5].aliases` в `config.yaml`**
— добавить русские формы официального названия. Это полезно **не только** для
e-disclosure, но и для RBC и любых других источников, где X5 могут
упоминать под полным юридическим именем. Предлагаемые алиасы:

```yaml
companies:
  - name: X5
    aliases:
      - X5
      - Х5
      - X5 Retail Group
      - X5 Group
      - X5 Retail              # ↑ существующие
      - Корпоративный центр ИКС 5      # ↓ новые из P7
      - Корпоративный центр Икс 5      # вариант с маленькой к
      - ИКС 5                          # с пробелом
      - ИКС-5                          # с дефисом
      - ИКС5                           # без пробела (использует часть источников)
      - X5 Corporate Center
```

**По вариантам форматирования:** регистр (ИКС / Икс / икс) **не нужен
отдельным алиасом** — keyword match через `re.IGNORECASE`.

**Как работает наш filter с этим списком:**

| Алиас | Path | Что ловит |
|---|---|---|
| `Пятёрочка`, `Шехтерман` | Cyrillic single-word → **pymorphy3 lemma** | Все падежи (`Пятёрочки`, `Шехтермана` etc.) |
| `Корпоративный центр ИКС 5` | Multi-word → **regex token-boundary** | Только nominative-форму как литеральную строку |
| `ИКС 5`, `ИКС-5`, `ИКС5` | Multi-word с цифрами → **regex token-boundary** | Литеральную форму |

**Архитектурное обоснование:** короткие алиасы (`ИКС 5`, `ИКС-5`, `ИКС5`)
— это **shortcut'ы** на все падежные формы длинного юридического имени.
Текст «Корпоративного центра ИКС 5» (genitive) **не сматчится** на длинный
алиас «Корпоративный центр ИКС 5», но **сматчится** на короткий «ИКС 5»
который буквально присутствует во всех падежах фразы. Длинный алиас оставляем
для дополнительной точности на nominative.

Если в будущем потребуется multi-word declension matching — это отдельная
задача (нужно лемматизировать каждый токен фразы и искать последовательность
лемм в тексте). На MVP не требуется.

поправки. Также: принимаешь ли подход «найти ID через Playwright в T7.2 и
заложить в config»?

## Безопасность (CSO review отдельным шагом)

Новые риски от Playwright:

| Риск | Митигация |
|---|---|
| Browser-process arbitrary file read через `--allow-file-access-from-files` | Не передавать; Playwright по умолчанию blocked |
| Загрузка вредоносного контента через `<iframe>` от servicepipe | Playwright sandboxed; ничего не выполняем вне нашего скрипта |
| Утечка credentials в browser cache | `context.clear_cookies()` в `__exit__`; persistent storage отключён в варианте P6.A |
| RCE через Playwright если patched binary | Используем pip-installed playwright + `playwright install chromium` (signed binary) |
| Зависимости (~200MB Chromium) — supply chain | Playwright — Microsoft project, активно поддерживается, ставится из pypi |
| Browser timeout / hang на page.goto | Жёсткий timeout (30s) + `context.close()` в finally |

Дополнительно: anti-bot detection arms-race. Если e-disclosure сделает шаг сложнее (например, fingerprinting WebGL, headless detection) — придётся ставить playwright-stealth или менять профиль. Это **технический долг**, который примем когда наступит.
